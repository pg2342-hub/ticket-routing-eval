Ticket Routing Threshold Eval

One decision: which product team should own an incoming support ticket, and how sure the model has to be before it routes the ticket without a person looking at it. It takes a model's answers in the shape of a System One choice answer, as documented in OpenRouter's System One API reference (a choice, a confidence, and the probability of every option), then shows, at each confidence threshold, how many tickets would be routed automatically, how accurate those routes are, and what 1,000 tickets cost in triage time, misroutes and model spend.

What the baseline shows

The baseline is a cheap bag-of-words classifier with isotonic calibration. It is a floor to beat, not a proposal.

  1. Routing everything is worse than routing nothing. With these cost assumptions, a model that is right 75% of the time costs $1,243 per 1,000 tickets against $991 by hand. Break-even for routing everything is about 80% accuracy, because a misroute costs five times a manual triage.
  2. A threshold picked once does not hold. The threshold picked on older issues (0.70) misses a 95% bar on newer ones (93.1%, bootstrap 95% range 89% to 97%), while 0.85 would have cleared it. The validation pick cleared 95% by one ticket (82 of 86), and overall accuracy fell from 85% on the validation slice to 75% on the test set as the team mix shifted. Part of the gap is noise and part is drift; both are why a pilot re-checks the threshold every week on the latest routes.
  3. Confidence has to mean something. The calibration table below checks that tickets the model is 90% sure of are right about 90% of the time. The baseline's expected calibration error is 0.061.

Caveats

The test set is 319 issues, so every number has a wide range. 68 of the 108 correct routes at 0.85 are feature-flags issues, and the baseline is weaker outside that team. Isotonic calibration fitted on 743 issues is fragile (sigmoid calibration gives a very different curve), which is one more reason to prefer a model whose confidence is calibrated by design and to check it on the customer's own tickets.

Threshold picked on the validation slice (149 older tickets): 0.70. On the test tickets it routes 54% automatically at 93.1% accuracy (161 of 173), which misses the 95% bar (bootstrap 95% range 89% to 97%), and saves $351 per 1,000 tickets. In hindsight, the lowest threshold that clears the bar on the test tickets is 0.85 (35% routed at 97.3%, 108 of 111). The validation pick cleared the bar by a small margin on few tickets, and the team mix also shifted between older and newer tickets, so a threshold chosen once is not enough evidence; a pilot re-checks it every week on a few hundred routes.

Data

1,062 public GitHub issues from PostHog's main repository that carry exactly one team/* label, across 10 teams (product analytics, feature flags, experiments, data warehouse, web analytics, LLM analytics, session replay, error tracking, conversations, CDP). Each issue stands in for a support ticket, and its team label is the ground-truth owner. Title prefixes that name the product outright ("Feature flags: ...") are removed, along with links and images. GitHub search returns at most the 200 newest issues per team label, so large teams are capped and the team mix shifts between older and newer issues; treat the mix as a sample, not PostHog's real ticket volume.

The split is by date. The oldest 70% (743 issues, through June 2026) train the baseline, and the newest 30% (319 issues, July 1 to November 17, 2026) are the test set, so the test looks like next month's queue, including teams that grew after the training data was collected. The confidence threshold is picked on a validation slice (the newest 149 training issues) and only then applied to the test set, the way a pilot has to pick it before next month's tickets arrive.

These are GitHub issues, not PostHog's private support tickets, so the numbers show the method rather than PostHog's real routing accuracy. A pilot reruns the same script on the customer's own closed tickets.

python run_eval.py --val-answers val_answers.jsonl --answers test_answers.jsonl --out reports_jev
python run_eval.py --confidence top   # threshold on the top probability instead of the confidence field

The harness takes answers in the shape of a System One choice answer (OpenRouter's System One API reference): a choice, a confidence, and the probability of every option. An answers file has one line per ticket:

{"id": 41234, "answer": {"type": "choice", "choice": "feature-flags", "confidence": 0.75, "probabilities": {"feature-flags": 0.84, ...}}}

Jev's confidence is reported separately from its top probability, so the harness thresholds on confidence by default and can sweep the top probability too. A {"type": "refusal"} answer, or an answer with neither a confidence nor probabilities, is always sent to a person.
